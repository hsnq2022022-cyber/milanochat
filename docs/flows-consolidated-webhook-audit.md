# Combined legacy webhook safety candidate — review only

## What changed and what did NOT

This branch combines the existing security fixes from PR #129 + PR #130 with PR #134 passive flow shadow gate and PR #135 PostgREST duplicate handling in **one copy of the same** `milan-api/index.ts`. A merge of separate stale `index.ts` copies could erase another fix; this branch prevents that class of integration error.

1. Instagram/Facebook POST signature verified against configured app secrets; no fail-open when none is set. Missing secrets return HTTP 503.
2. WhatsApp Cloud API POST signature verified against raw-body HMAC-SHA256 **before** the message loop; wrong signature returns 401; missing secret 503. GET handshake unchanged.
3. Incoming messages must be persisted successfully before starting the AI responder. PostgREST SQL errors (including unique `wa_message_id` 23505) now abort the reply. No new duplicate AI response is generated by this error path.
4. Passive flow shadow gate is **OFF** unless server environment is exactly `FLOW_SHADOW_MODE=observe`. OFF mode performs zero additional database reads. ON mode reads two server-controlled switches for a verified test-only account and may log eligibility, but it **does not reply, send, debit or change the AI responder**.
5. Successful original AI/RAG/Meta/WhatsApp reply and existing billing path are otherwise unchanged.

## GO / risks

- The entire integration touches `milan-api`: not merged/deployed without a separate explicit owner GO. No live SQL, Meta subscription, customer messages or credits were changed.
- Strict signature validation may cause legitimate Meta events to fail if secrets are missing or wrong. Inspect secret metadata **without revealing values**, test signed IG/FB/WA webhooks, GET verify and retry on test-owned accounts before deploying.
- The unique index only protects inbound events that have a `wa_message_id`. Events with no external ID still need the transactional receipt/outbox for true idempotency.
- Existing **outgoing** messages and billing RPC are not fixed by this patch: see PR #131 and the durable worker contract PR #127.
- When the shadow mode is OFF, no new DB reads or webhook side effects occur; it requires additive OFF switches in PR #133 to observe a test account.
- Rollback: record the currently deployed function SHA/previous stable revision; preserve data and revert only the deployed function after owner GO. Do not revert into an unsigned-webhook state without explicit security risk acceptance.

## Release blockers still open

No authenticated publication API, no live durable transaction integrating receipt/run/outbox, no Meta provider crash reconciliation, no credit ledger audit against actual sent IDs, no signed all-channel canary and no owner-approved site deployment. The system is **not ready for customer-facing automation**.
