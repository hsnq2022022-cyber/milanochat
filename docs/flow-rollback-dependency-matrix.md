# Flow rollback dependency matrix (V3/V4 migrations)

Derived 2026-11-26 from the migration and rollback SQL in this repository (status labels: **CONFIRMED**, **FALSE POSITIVE**, **UNCERTAIN**). Nothing here ran against production.

## What this document is, and what it is not
- The original "23 suspected older rollback dependency pairs" came from an unrecorded heuristic ("later-migration -> earlier-migration references without an explicit `roll back X first` text", docs/flow-v3-v4-activation-readiness.md section 10). The 23 pairs were **never enumerated in the repository and cannot be reconstructed**; no pair list is invented here.
- Instead the pairs were re-derived mechanically: for each Flow migration E and each later Flow migration L, a pair is listed when L mentions an object E creates **and** E's rollback drops or restores that object. That name-reference rule found **78 candidate pairs over 16 earlier migrations** (it over-counts: a mention is not a break).
- Classification is behavioural, not textual: `tests/flow-lifecycle-integration.test.ts`, step "rollback closure over the whole Flow chain", applies the **full** chain (every Flow migration installed) to a disposable PostgreSQL, runs each rollback out of order, and asserts the pinned outcome below. REFUSED rollbacks must change nothing (catalog fingerprint equal); ACCEPTED rollbacks must leave **no remaining function body referencing an object they dropped** (the defect class fixed in PR #211 for 340000 -> 360000). The same step proves the detector works (drops the 340000 table and expects `flow_inbound_recovery_lease` to be reported) and that the strict reverse order of all 24 chain rollbacks applies cleanly.
- Mutation evidence: restoring the pre-PR-#211 340000 rollback makes both this step and the existing "rollback order" step fail.

## Result
- **76 candidate pairs: CONFIRMED and protected** (earlier migration's rollback refuses while the later one is installed).
- **2 candidate pairs: FALSE POSITIVE at SQL level** (rollback is accepted, but nothing in SQL depends on what it drops or restores; evidence below).
- **0 unprotected SQL dependencies remain.** The only real one was 340000 -> 360000 (fixed in PR #211, rollback file only; never applied anywhere).
- **UNCERTAIN (not provable from SQL):** Edge Function code that calls an object a rollback drops (for example milan-api and the workers calling functions of 330000/350000/150000). Those paths are gated OFF/canary-only and are covered operationally by the documented strict order, not by SQL.

## Maintenance
Adding a Flow migration to the lifecycle `CHAIN` requires classifying its rollback in the closure step (the step fails on an unclassified rollback). A new REFUSED/ACCEPTED entry is a reviewable decision, not an automatic pass.
