### Root causes (confirmed with production evidence)
- **Why Instagram stopped replying:** since r4 was activated every Instagram DM starts a durable run that sleeps 1 minute; the wake cron `milanochat-flow-durable-wake-v1` calls `flow-runtime-worker` every minute and gets **HTTP 401** (357 of the last 24 h; one stray 503), so the delayed message is never produced; because the durable path "handled" the DM, neither the V2 flow nor the normal AI answers. Last automatic Instagram reply: 2026-11-09 16:27:27 UTC; last inbound: 2026-11-10 12:25:59 UTC. A newer DM in the same conversation supersedes the previous sleeping run. The local uncommitted work cannot be the cause (production runs the old deployed code; none of it is deployed).
- **401:** both workers accept `Bearer <SUPABASE_SERVICE_ROLE_KEY env>` or `Bearer <Edge secret flow_worker_service_role_key>` (`supabase/functions/flowWorkerAuth.ts`; an empty cron key never grants access). The cron sends the Vault secret `flow_worker_service_role_key` (exists; it is a legacy `service_role` JWT for this project, iat 2026-09-05, **sha256 prefix 1d8486952ca0**). The owner's Edge-secrets listing has NO secret of that name, and the runtime service-role key evidently differs from the Vault JWT. Both conditions together give the 401. The runtime key itself cannot be read from here → exact cause of "key differs" is UNVERIFIED, but creating the Edge secret from the Vault value is the supported fix. The outbox worker uses the same function/secret (also 401; not yet exercised because no message rows exist).

## 6. Risks and safety restrictions
- Production is LIVE; one tenant uses flows. Fixing the 401 without containment releases stale messages (see A).
- Retry policy returns HTTP 503 so Meta redelivers; one retryable event can make a whole webhook batch 503 (E4 must process the full batch first); Meta's behaviour on repeated 503s (throttling/disabling the shared webhook) is UNVERIFIED.
