# Milano Server — Backend

خادم Node.js/Express يربط الواجهة الحالية بنظام حقيقي: واتساب (Baileys)، قاعدة معرفة دلالية (Supabase + pgvector)، رد آلي مُقيّد بالمعلومات، رصيد ردود، ولوحة تحكم (Supabase Auth) مع دفع Moyasar.

---

## ⚠️ تنبيه صريح قبل أي شيء

طريقة الربط الحالية (Baileys / خاصية **الأجهزة المرتبطة**) **غير رسمية من Meta** وقد تخالف شروط استخدام واتساب، وفيها **خطر حقيقي لتقييد أو حظر الرقم** — خاصة مع الأرقام الجديدة أو حجم رسائل عالٍ. التخفيف الممكن: رقم مخصص للمشروع، إحماء تدريجي، بلا إرسال جماعي.

**البديل الرسمي (مسار الترقية المخطط):** [WhatsApp Business Cloud API](https://developers.facebook.com/docs/whatsapp/cloud-api)

| | Baileys (الحالي) | Cloud API (الرسمي) |
|---|---|---|
| الاعتماد | غير رسمي، بلا ضمانات | رسمي من Meta بعقد واضح |
| خطر الحظر | موجود فعليًا | شبه معدوم عند الالتزام بالسياسات |
| التكلفة | مجانية (تكلفة تشغيل السيرفر فقط) | رسوم لكل محادثة حسب الفئة (تسويق/خدمة/منفعة) — غالبًا بضعة سنتات للمحادثة، مع فئات خدمة مجانية ضمن حدود |
| الموثوقية | تعتمد على بقاء الجلسة وجهازك | SLA رسمي وبنية Meta نفسها |
| الحدود | بلا حدود معلنة (والمراقبة غير معلنة أيضًا) | حدود رسائل متدرجة (250 → غير محدود) حسب جودة الحساب والتوثيق |
| المتطلبات | مسح QR من الهاتف | توثيق النشاط التجاري وحساب Meta Business |

التصميم الحالي يفصل **محرك الرد** عن **ناقل الإرسال** (`sessionManager`)، فالتبديل لاحقًا = استبدال ناقل فقط دون لمس منطق الرد أو قاعدة المعرفة. لن أطبق Cloud API الآن إلا بطلبك.

## القرارات المتخذة (قابلة للتغيير من env فقط)

- **مزوّد LLM:** محايد — الافتراضي أي مزوّد متوافق مع OpenAI (`gpt-4o-mini`)، وبدون تغيير كود يتحول إلى Anthropic (`LLM_PROVIDER=anthropic`). إن كنت تفضل مزوّدًا محددًا غيّر متغيرين.
- **Embeddings:** متوافقة مع OpenAI (`text-embedding-3-small`) — تدعم Voyage AI بتغيير القاعدة والموديل.
- **الدفع:** Moyasar (سعودي، webhook بسيط بتوقيع HMAC). حقل `provider` في جدول المدفوعات جاهز لإضافة Tap/PayTabs.

## خطة التنفيذ على مراحل

### المرحلة 0 — الأساس *(مكتملة في هذا الكود)*
- مخطط قاعدة البيانات كامل (`supabase/schema.sql`): عزل multi-tenant، pgvector، دالة خصم ذرّية بلا ازدواج، بحث دلالي مقيد بالعميل، RLS.
- تشفير حقلي AES-256-GCM لأرقام واتساب ومحتوى الرسائل عند الراحة.
- مدير جلسات Baileys: QR حقيقي لكل عميل، مفاتيح دائمة (`data/auth/<tenantId>`) فلا QR جديد بعد إعادة التشغيل، إعادة وصل تلقائية، واستعادة الجلسات عند الإقلاع.
- خط المعرفة: استخراج نص من الرابط (cheerio) → تقطيع متراكب → embeddings → تخزين.
- محرك الرد: بحث دلالي ← LLM مُقيّد بالسياق بصيغة JSON (grounded/answer) ← إن لم يتأكد يرد بالاعتذار الرسمي ويسجل السؤال في **سجل الأسئلة العالقة** ← الطلب الصريح لموظف بشري أو كلمات حساسة (شكوى/استرجاع) يوقف الرد الآلي ويعلّم المحادثة **محوّلة**.
- الرصيد: الخصم عبر `consume_reply()` الذرّية **بعد التسليم الفعلي فقط**، والإيقاف التلقائي عند الصفر.
- Moyasar: فاتورة ← webhook موقّع HMAC ← تفعيل + منح رصيد (idempotent).
- Rate limiting على الـ webhooks ومسارات الإنشاء وQR.

### المرحلة 1 — تفعيل MVP (خطواتك الآن)
1. Supabase: أنشئ مشروعًا وفعّل pgvector، ثم نفّذ `supabase/schema.sql` كاملًا.
2. `cd server && npm install && cp .env.example .env` واملأ المفاتيح.
3. `npm run dev` — السيرفر على المنفذ 4000.
4. في جذر المشروع أضف `.env` فيه `VITE_API_URL=http://localhost:4000` ثم أعد بناء الواجهة.
5. جرّب من الواجهة: إنشاء عميل ← فهرسة مصدر ← مسح QR حقيقي من واتساب (الأجهزة المرتبطة) ← أرسل رسالة من رقم آخر وراقب الرد والخصم.
6. للاختبار من الإنترنت (webhook الدفع): `ngrok http 4000` وضع الرابط في `PUBLIC_URL`.

### المرحلة 2 — لوحة التحكم الكاملة + الدفع الإنتاجي
- صفحات `/dashboard` في الواجهة: تسجيل Supabase Auth، ضم الحساب عبر `claimToken`، عرض الرصيد والاتصال، سجل المحادثات، الرد اليدوي مع "استئناف الرد الآلي"، حل الأسئلة العالقة (مع زر "أضفها للمعرفة" فيتعلم الموظف فورًا)، شراء شحنات عبر Moyasar بمفاتيح الإنتاج.
- إشعار عند نفاد الرصيد داخل اللوحة (الباك-إند يعلّم المحادثات `auto_paused_reason=credits` جاهز).

### المرحلة 3 — تدعيم وإنتاجية
- ناقل Cloud API الرسمي بديل Baileys (نفس المحرك).
- استخراج بيانات بطاقة قوقل عبر Google Places API (روابط الخرائط تحتاج API رسمي — اليوم تُحفظ ويُفهرس ما يُستخرج من الصفحة).
- ملفات PDF/DOCX كمصادر معرفة، طابور BullMQ للفهرسة، Redis لمعدل متعدد النسخ، مراقبة وقياسات، واختبارات end-to-end.

## التشغيل السريع

```bash
# 1) قاعدة البيانات
#    افتح Supabase SQL Editor والصق supabase/schema.sql

# 2) الخادم
cd server
npm install
cp .env.example .env      # املأ كل المفاتيح
npm run dev               # http://localhost:4000/health للتأكد

# 3) الواجهة (من جذر المشروع)
echo "VITE_API_URL=http://localhost:4000" > .env
npm run dev
```

مفاتيح التشفير: أنشئ `FIELD_ENCRYPTION_KEY` بأمر `openssl rand -hex 32` ولا تدره أبدًا — دونه لا تُفك البيانات المخزنة.

## الأمان والامتثال

- أرقام واتساب ومحتوى الرسائل والأسئلة العالقة: **مشفر AES-256-GCM عند الراحة** داخل Supabase (الذي يوفر تشفير قرص على مستوى المنصة + RLS مفعّلة).
- سياسة خصوصية متوافقة مع PDPL: `PRIVACY_POLICY_ar.md` (تُعرض على `/privacy`).
- الـ webhook لا يقبل حدثًا بلا توقيع، والتفعيل **idempotent**، ومعدل محدود.
- LLM لا يستلم إلا القطع المعرفية ذات الصلة — لا سجل المحادثات كاملًا ولا أرقام العملاء.

## ربط واتساب الحقيقي — WhatsApp Session API

الواجهة (React) **لا تنشئ أي جلسة** — فقط تعرض ما يبثه الخادم. الجلسة ومفتاحاها يعيشان في الخادم.

### المسارات (كلها محمية: توكن Supabase أو توكن جلسة المعالج، ومعرف الجلسة يجب أن يطابق Tenant المصرح به)

| الطريقة | المسار | الوصف |
|---|---|---|
| POST | `/api/whatsapp/session` | إنشاء/استرجاع جلسة (تنشئ مقبس Baileys فعليًا) |
| GET | `/api/whatsapp/session/:sessionId` | الحالة الحالية |
| GET | `/api/whatsapp/session/:sessionId/qr` | آخر QR حقيقي (PNG data URL) |
| POST | `/api/whatsapp/session/:sessionId/logout` | فصل الجهاز ومسح المفاتيح نهائيًا |
| GET | `/api/whatsapp/session/:sessionId/events` | **بث SSE لحظي**: لقطة فورية ثم كل تغيّر حالة وكل QR جديد فور صدوره (نبض 25 ث) |

هنا `sessionId = tenantId` — لكل Agent/Workspace جلسة Baileys مستقلة تمامًا (مقبس ومفاتيح ومستستمعون منفصلون).

### آلة الحالات

`QR_REQUIRED → CONNECTING → CONNECTED` مع `DISCONNECTED` (إعادة وصل تلقائية بتأخير متدرج 2/4/8/16/30 ث)، `LOGGED_OUT` (فُصل من الجوال → تُمسح المفاتيح ويُصدر رمز جديد)، و`ERROR` (تعذر إنشاء الجلسة). انتهاء صلاحية QR يعالج نفسه: Baileys يصدر رمزًا جديدًا كل ~20 ثانية ويُبث فورًا عبر SSE دون تحديث الصفحة.

### من أين يأتي QR؟

الرمز **يُصدر من جلسة واتساب نفسها** (الحدث `connection.update` في Baileys يحمل النص الخام الذي تولّده خوادم WhatsApp Web)، ومكتبة `qrcode` لا تفعل أكثر من رسمه PNG — هذا هو الربط الفعلي الوحيد الممكن عبر الأجهزة المرتبطة.

### أين يُشغَّل الخادم؟ (مهم)

الواجهة تُبنى إلى `dist/` ثابت — **GitHub Pages وأي استضافة ثابتة لا تشغّل Node.js**. إذًا:
- الواجهة: أي استضافة ثابتة (GitHub Pages / Netlify / Vercel static).
- الخادم: VPS أو Railway/Fly/Docker — شغّله بـ `npm run dev` (تطوير) أو عبر pm2/Docker (إنتاج)، ثم اجعل `VITE_API_URL` في الواجهة يشير إليه، و`PUBLIC_URL` و`FRONTEND_ORIGIN` في `.env` الخادم يطابقان الواقع.

### قائمة الاختبار اليدوي

```bash
TOK=<claim_token من إنشاء العميل>   # أو توكن Supabase
API=http://localhost:4000

# 1) إنشاء جلسة → تعود الحالة (تبدأ بـ QR_REQUIRED بعد لحظة)
curl -X POST $API/api/whatsapp/session -H "content-type: application/json" \
  -H "x-tenant-token: $TOK" -d '{"tenantId":"<ID>"}'

# 2) البث اللحظي — راقب QR يتغير كل ~20 ثانية والحالة تتنقل
curl -N "$API/api/whatsapp/session/<ID>/events?token=$TOK"

# 3) مسح QR من الجوال → تظهر CONNECTING ثم CONNECTED مع رقم مقنّع
# 4) أعد تحميل الصفحة → نفس الحالة (البث يعيد اللقطة فور الفتح)
# 5) أعد تشغيل الخادم → يعود CONNECTED بدون QR (المفاتيح في data/auth/<ID>)
# 6) افصل الجهاز من الجوال → LOGGED_OUT ثم QR جديد تلقائيًا
# 7) تسجيل الخروج:
curl -X POST $API/api/whatsapp/session/<ID>/logout -H "x-tenant-token: $TOK"
# 8) أنشئ عميلين واربطهما معًا → جلستان مستقلتان لا تتداخلان
# 9) جرّب توكن عميل آخر على جلسة لا يملكها → 403
```
